## 零、你报的「点开始录屏没反应」——已定位并修复

**先说结论:录屏本身没坏,是「失败了却完全不说」+「UI 骗人」的连锁反应。**
我用你自己的机器完整复现了一遍。

### 复现出来的现象链

| 你点了之后 | 实际发生了什么 |
|---|---|
| 第 1 次点「开始录屏」 | 气泡和录制按钮都出现了,但 **ffmpeg 在后台立刻退出**(音频设备被占用/名字不对等),抓帧线程跟着死掉 |
| 此时界面 | **录制按钮仍然挂着**,看起来还在录 —— UI 在骗人 |
| 同时 `_last_fail` 被记下 | `START_FAIL_COOLDOWN = 60`,接下来 **60 秒内的每一次点击都静默返回 None** |
| 第 2 次点「开始录屏」 | `start()` 返回 `None`,`_toggle_record` 里 `if path:` **不成立就什么都不做** → 这就是你看到的「没反应」 |
| 想知道为什么 | 错误只有一句 `print`,而打包版 `console=False` **根本没有控制台** → 永远看不到 |

在 `pet.py` 里就是这一处:

```python
path = rec.start()
if path:
    ...弹气泡、显示按钮...
# ← 没有 else。失败时静默,这就是「没反应」的根因
```

### 验证过的事实

- 你的环境**本身是好的**:RTX 4060 的 NVENC 可用、VB-Cable 装着、dxcam 能抓到 1920×1080、
  手动调 `start()` 能录出正常的 mp4
- 但把音频设备名字改错后,100% 复现「第 1 次看着像成功、第 2 次完全没反应」

### 这次改了什么

| 改动 | 效果 |
|---|---|
| `start()` 失败时把原因写进 `last_error` | 不再只有一个 `print` |
| `pet.py` 补上 `else` 分支,弹气泡显示原因 | **点下去一定会有反馈**,哪怕是失败 |
| 录制按钮在抓帧线程意外死亡时自动收起并提示 | UI 不再假装还在录 |
| 冷却时间 60 秒 → 15 秒,并且冷却中也会提示「X 秒后再试」 | 连点不再石沉大海 |
| 启动前先用 `ffmpeg -list_devices` 校验音频设备名(结果缓存,启动时后台预热) | 名字不对就直接**只录画面**,不再白跑一趟 |
| 带音频启动失败时自动退回「只录画面」 | 音频坏了也**照样能录下来** |
| 录到一半音频断了 → 自动换只录画面接着录 | 不用重新点 |
| ffmpeg 的 stderr 从 `DEVNULL` 改为写 `recordings\ffmpeg.log` | 以后再出问题**查得到原因** |
| 首帧 `cam.grab()` 返回 None 时重试 60 次(原来一次就判死) | 桌面静止时不会误判初始化失败 |
| 视频输入加 `-use_wallclock_as_timestamps 1` | **修掉录出来是快进/卡顿的问题**(见下) |
| 新增设置 `intervals.record_audio_device`,填 `""`/`none` 就只录画面 | 不用再改代码 |
| **`dxcam.create()` 显式指定 `processor_backend="numpy"`** | 修掉打包版「没有 cv2 模块」的崩溃(见下) |

### 打包版专有:「录屏失败:没有 cv2 模块」

这个是**只在打包版出现**的,源码跑得好好的,所以第一次打包时没暴露。

根因是 dxcam 的一个动态导入:

```python
# dxcam/processor/cv2_processor.py:109
self._cv2 = import_module("cv2")     # ← 动态导入,PyInstaller 静态分析看不见
```

- `dxcam.create()` 的 `processor_backend` **默认就是 `"cv2"`**
- PyInstaller 看不到这个 `import_module("cv2")`,所以包里没有 cv2
- 结果:打包版一 `grab()` 就 `ImportError: No module named 'cv2'`
- 而你的 Anaconda 里装了 cv2 4.13.0,所以源码环境永远正常 —— 典型的「开发能跑、打包就崩」

**修法**:建摄像头时显式指定 numpy 后端。

```python
dxcam.create(output_color="BGR", processor_backend="numpy")
```

实测(把 cv2 屏蔽掉模拟打包环境):

| 后端 | cv2 缺失时 |
|---|---|
| `cv2`(dxcam 默认) | `grab()` 抛 `ImportError` |
| `numpy` | 正常抓到帧 `(1080, 1920, 3)`,像素值正确 |

numpy 后端走的是 `dxcam.processor._numpy_kernels` 这个 Cython 内核
(spec 里已经手动打进包了),完全不需要 cv2,而且比把整个 opencv
塞进安装包**省 60~100 MB**。

> ⚠️ 有个连带风险:如果这个内核**没**打进包,dxcam 会**悄悄退回 cv2 后端**
> (日志里只有一行 warning),录屏照样失败。所以启动时会往 `boringpet.log`
> 写一行 `[录屏] dxcam numpy 内核: ok` 方便定位 —— 打包版实测输出确实是 `ok`。

### 顺带修掉的一个画质 Bug

原来给 ffmpeg 的输入固定标称 60fps,但 Python 往管道里写 1920×1080 的裸帧**根本达不到 60fps**
(每帧 6.2 MB,还要 `tobytes()` + 写管道 + flush)。结果 ffmpeg 按 60fps 解释实际只有约 20fps 的帧流,
**录出来的视频是快进的**。

实测:录 6 秒只生成 1.07 秒视频(约 0.3 倍速)。加上 `-use_wallclock_as_timestamps 1`
让 ffmpeg 按帧到达时间打时间戳后,现在录 4 秒就是 3.98 秒,**播放速度正常了**。

## 一、会崩溃 / 会丢数据

### ✅ 1. 录屏满 45 秒后桌宠会卡死 —— `pet.py` 的 `rec.MAX_DURATION`

`ScreenRecorder` 里根本没有 `MAX_DURATION` 这个属性,它只是 `screen_recorder.py`
的**模块级**常量。而 `tick()` 里是按实例访问的:

```python
if rec.is_recording and rec.can_stop() and (
        self._last_hr_value < 105 or rec.elapsed >= rec.MAX_DURATION):   # ← AttributeError
```

触发条件很常见:**录到 45 秒以上、心率又降下来了**。一旦抛异常,`tick()` 在
`place()` 之前就中断 → 桌宠动画冻住,而且「录满 1 小时防磁盘录满」的兜底永不生效。

已修:在 `ScreenRecorder` 类体里加上 `MIN_DURATION` / `MAX_DURATION` 类属性。

### ✅ 2. 打包后 token 用量统计每次清零 —— `token_stats.py`

```python
def _usage_file():
    return Path(__file__).parent.parent / "memory" / "usage.json"   # ← 不能用 __file__ 推
```

打包后 `__file__` 指向 `_MEIPASS` 临时解压目录,写入的 `usage.json` 退出即被删,
**每次启动统计都从零开始**。项目里 `memory.py` / `chat_window.py` / `divination.py`
都老老实实用了 `paths.app_dir()`,只有这里漏了。

已修:改用 `app_dir() / "memory" / "usage.json"`。

### ✅ 3. 别人电脑上根本起不来 —— `main.py` 顶层 `import torch`

```python
import torch   # 第 7 行,无条件导入
```

`requirements.txt` 里**没有 torch**。torch 安装包 3~5 GB,不可能让别人装。
而且 `src/memory.py` 第 265-268 行自己写着:向量检索已改成云端 API,
「彻底绕开本地 torch/transformers」。**也就是说 torch 已经完全没人用了**,
只剩这一行历史残留,却会让干净环境直接 `ModuleNotFoundError` 崩在启动第一行。

已修:改成 `try: import torch / except Exception: pass`(本机行为不变,别人机器上跳过)。

### ✅ 4. 两份 memory 模块实例,锁各管各的 —— `main.py`

`main.py` 有 `sys.path.insert(0, "src")`,所以 pet/chat_window 里是 `import memory`,
而 `main.py` 自己写的是 `from src import memory as mem`。
Python 会当成**两个不同的模块**分别加载 → 两个 `_IO_LOCK`、两份缓存。

后果:退出时的 `_finalize_memory` 用 A 实例的锁写 `raw_history.json`,
后台提取线程用 B 实例的锁写同一个文件 —— 锁形同虚设,可能互相覆盖。
（`memory.py` 第 26-28 行的注释明确说这把锁是用来防这个的。）

已修:统一成 `import memory`。

### ✅ 5. 「时间代谢」从来没运行过 —— `pet.py`

```python
def _check_active_events(self):
    # 0. 时间代谢: 情绪冷却 + 想念值随时间增长 (60 秒节流结算)
    try:
        if now - getattr(self, "_last_meta_tick", 0.0) >= 60.0:
            self._last_meta_tick = now
            tick_hormones()          # ← NameError!pet.py 里没导入过这个名字
    except Exception:
        pass
```

`tick_hormones` 只在另一个方法的**函数内部**被 import 过(局部作用域),模块层没有。
所以这里每次都是 `NameError`,被 `except Exception: pass` 静静吃掉。
**结果是情绪衰减和想念值增长一次都没执行过** —— 注释承诺的功能是空的。

已修:函数内 `from memory import tick_hormones`。

### ✅ 6. 游戏评论间隔设置不生效 —— `pet.py`

`self._game_comment_min / _max` 只在 `_apply_settings()`(用户点保存)里赋值,
`__init__` 里没有。所以**每次启动后一直用写死的兜底值 2~10 分钟**,
你 `settings.json` 里配的 5~15 分钟要等你在设置窗口点一次保存才开始生效。

已修:`__init__` 里从 `self._user_settings["intervals"]` 初始化。

### ⚠️ 7. 退出时 Qt 崩溃(QThread 还在跑就被销毁)—— **未修,建议修**

`QThread: Destroyed while thread is still running` → 进程以 `0xC0000409` 直接终止。
子代理用 PySide6 6.7.2 复现过。三个地方:

| 位置 | 问题 |
|---|---|
| `chat_window.py:764` / `closeEvent:1094` | `ChatWorker` 请求中(`urlopen` 超时 300 秒)时关窗口/退出 → 线程还在跑 |
| `active_chat.py:354 / 414 / 487` | worker 以 pet 为 parent 且从不删除;`_generate_diverse` 最多 4 次连续 HTTP(每次超时 90 秒) |
| `heart.py:326-330` | `stop()` 既不 join 也不停 `_scanner`;蓝牙连着时线程会活到 10 秒超时 |

另外 `pet.py:1602` 的 `w.requestInterruption()` 是**空操作** ——
全项目没有任何一个 worker 检查过 `isInterruptionRequested`(grep 结果 0 处)。

修法:`worker.finished.connect(worker.deleteLater)`、构造时不传 parent、
`run()` 里检查 `isInterruptionRequested()`、`closeEvent` 里 `wait(2000)`。

### ✅ 15. 「游戏优化」的 Nagle 项从来没能生效 —— `src/game_boost.py`

```python
def _reg_cmd(args):
    reg = shutil.which("reg") or "reg.exe"
    return _run_cmd([reg] + args)          # ← 列表 + 字符串 → TypeError
```

### ✅ 16. `_run_cmd` 在中文系统上会静默返回假成功 —— `src/game_boost.py`

`music_player.py` 的 `os.makedirs(MUSIC_DIR)` 和 `divination.py` 的

### ✅ 18. 歌词会晚最多 0.9 秒 —— `src/music_player.py`

```python
ms = int(m.group(3))
time_sec = minutes * 60 + seconds + (ms / 100.0 if ms < 100 else ms / 1000.0)
```

LRC 的小数位有 `.xx`(百分秒)和 `.xxx`(毫秒)两种写法,按**数值大小**猜是错的:
`.049` 是 49 毫秒(0.049 秒),代码却按 `ms < 100` 当成 0.49 秒。
你自己的歌词文件里就有: `T.R.Y. - 不是因为寂寞才想你.lrc` 的 `[01:22.049]`、
`[02:27.010]`,还有 `mj apanay...lrc` 的 `[01:18.058]`。
已修:按**小数位数**换算 `int(frac) / 10**len(frac)`。

已修:抽出 `_asset_dir()` 统一走回退逻辑。

### ✅ 20. `__file__` 推路径的最后几处 —— `src/dsh_chat.py`、`src/paths.py`

- `DSH_CWD = Path(__file__).resolve().parent.parent`:打包后算出来是**安装目录**,

### ✅ 21. `sys.path.insert(0, "src")` —— `src/usage_window.py`

## 三A、还需要注意的设计问题(未改)

### ⚠️ `app_dir()` 没有可写目录兜底 —— `src/paths.py`

所有可写数据(`settings.json`、`memory/`、`recordings/`、`音乐/`、日志、
`usage.json`、`divination.db`)全都在 exe 同目录。放在 Program Files 下就全线失败。
建议加一个 `data_dir()`:`app_dir()` 可写就用它,否则退回
`%LOCALAPPDATA%\BoringPet`,所有可写路径统一改用它。

### ⚠️ 录屏抓帧线程会空转烧 CPU —— `src/screen_recorder.py:151-166`

`dxcam.grab()` 实测约 0.05 ms 一次,而循环里那个 `if now - last_t >= frame_interval`
**只是跳过写入,并没有 sleep**。所以真正在打游戏(有帧可抓)时,这个线程会以
每秒上万次的速度空转,反而抢走游戏的 CPU。
建议:`time.sleep(max(0, frame_interval - (now - last_t)))`。

### ⚠️ 录屏音频设备写死 VB-Cable,失败还是静默的 —— `src/screen_recorder.py:31`

```python
AUDIO_DEVICE = "CABLE Output (VB-Audio Virtual Cable)"
```

对方没装 VB-Cable 的话 ffmpeg 立刻退出,而 `stderr=subprocess.DEVNULL` 把原因
也丢掉了,`start()` 还报成功。建议:把设备名做成设置项,并把 ffmpeg 的 stderr
写进日志文件。

### ⚠️ 切换「主动功能」提供商后,识图仍然打 DeepSeek —— `src/settings_window.py`

```python
if not s["active"].get("vision_base_url"):   # ← 永远不成立
```

`load_settings()` 总会把 `vision_base_url` 填成 DeepSeek 的地址,而设置界面
**根本没有这两个字段的输入框**,所以这行判断永远不会执行。
结果是:你把 provider 换成硅基流动,识图还是去打 `api.deepseek.com` + 旧 key,

## 五、体积体检

整个项目 **1.84 GB**,打包前建议先清理:

| 目录 | 大小 | 要不要打包 |
|---|---|---|
| `recordings/` | **1,438 MB** | ❌ 你的录屏,绝对不能打包 |
| `音乐/` | **177 MB** | ❌ 你的私人歌单,而且这是用户数据,应该让用户自己往里放 |
| `assets/` | 202 MB | ✅ 要打(其中 `notify_0` 9.7MB + `_raw_jpg` 2.9MB 可删) |
| `音乐素材/` | 0.6 MB | ✅ 要打 |
| `图标/` `心率图标/` | 18.8 MB | ✅ 要打(其中 10 张 PNG 每张 1~3 MB,是无用的装饰图,可以压) |
| `memory/` | 1.8 MB | ❌ 你的私人记忆和日记,必须排除 |
| `src/` | 0.8 MB | 代码本身 |

顺带:`assets/` 里 1,783 张 PNG(262×300 RGBA)平均每张 111 KB,偏大。
用 `oxipng -o4` 或 `pngquant` 无损/近无损压一遍通常能省 30~50%,
也就是能少 60~100 MB。这个不影响功能,想做再说。
